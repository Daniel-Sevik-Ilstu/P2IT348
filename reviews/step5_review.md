| 1 | Medium | src/main.py `run_step5` (lines ~196-217) | `run_step5` calls `train_all_from_split(split)` and so retrains all three models. When the whole pipeline runs (`--step` omitted), Step 4 has already trained the same models, so every model is fit twice. This costs runtime against the 15-minute budget. The two sets of models are also separate fits, so the Step 4 training report and the Step 5 numbers do not describe the same objects (random_state=42 should make them identical, but nothing checks that). I did not time it, so the size of the cost is unknown. | Have `run_step4` return its models and pass them to `run_step5` (`models` argument, train only when `None`), or load them from `save_models` output. |
| 2 | Medium | src/evaluate.py `pooled_table`, `confusion_table`, `evaluate_model` | The "test years only" guard `assert_test_years_only` is called only in `run_step5` and in `per_year_table`. The functions that build the main Step 5 table and the confusion table accept any `X_test`/`y_test`, and nothing checks `len(X_test) == len(y_test)`. Someone calling `pooled_table` with training rows would get a silent, leaky "test" table. Today's call path is safe, so this is defensive, not a live bug. | Give `pooled_table` and `confusion_table` a `years_test` argument and call `assert_test_years_only` inside, or at least check the lengths. (If this changes the PLAN signature, update PLAN.md.) |
| 3 | Medium | src/evaluate.py `sensitivity_tables`, results/step5_pooled_no_dup.* | The no-duplicate subset changes the class mix: precision drops from about 0.82 to 0.77 and F1 from 0.87 to 0.84, while 7,743 rows are removed. Because the balance is no longer 50/50, the drop in precision is partly a base-rate effect and not only "the model was relying on duplicates". Neither the code nor the table records how many malware and benign rows were excluded or kept, so a reader cannot separate the two effects. I am inferring this from the numbers; I did not compute the class counts. | Add `n_malware` and `n_benign` (kept) and the excluded counts per class to the sensitivity table, or print the majority-class accuracy for the subset next to it. |
| 4 | Low | src/evaluate.py `compute_metrics` (line 87) | `zero_division=0` matches PLAN.md, but it hides a degenerate result. If a model predicted no malware, precision would be reported as 0.0 with no warning, which looks like a real score. This does not occur in the current results (the confusion table shows tp > 0 for all models), and it matters most for small slices such as the per-year Step 6 tables. | Keep the setting (it follows PLAN), but add a column or a printed note when `tp + fp == 0` or `tp + fn == 0`, so a 0.0 from zero division is distinguishable from a true 0.0. |
| 5 | Low | src/evaluate.py `sensitivity_tables` (line 158) | If every test row is a duplicate (`keep` all False), `model.predict` on an empty array raises a sklearn error with an unclear message. There is also no check that `dup_mask` came from the same test years as `years_test`; `run_step5` relies on the unstated assumption that `df["year"].isin(TEST_YEARS)` selects exactly the rows in `split`. That holds now, but a split built with different test years would misalign the mask silently when lengths happen to match. | Raise a clear `ValueError` when `keep.sum() == 0`. Optionally have `run_step5` assert `len(dup_mask) == len(y_test)` before the call (the function already checks this, so only the comment/assumption needs to be explicit). |
| 6 | Low | src/main.py `run_step5` / src/evaluate.py `baseline_accuracy` | The majority-class baseline is printed but not saved to results/. The saved metrics table has no reference for accuracy, and the pooled set is exactly balanced (baseline 0.5), so the 0.86 accuracy cannot be read in context from the CSV alone. | Add a `baseline_accuracy` column or a one-row file in results/. |
| 7 | Low | src/evaluate.py, PLAN.md Step 5 | PLAN lists `run_evaluation(df)` as the entry point and says it also writes the Step 6 files and optional figure; the builder put the entry point in `main.run_step5` instead. PLAN also says pooled metrics weight years by size and the per-year table is the primary view; Step 5 output does not carry any note of this (the 2017-2018 rows are 80% of the pooled set). This may be an intentional step-by-step split, so I mark it Low. | Either add `run_evaluation` as planned or update PLAN.md to say the entry point is `run_step5`. Add a one-line note about the 80% weighting to the markdown output or the Step 5 doc. |
| 8 | Low (style) | src/main.py `main` | `df = run_step1()` is now unconditional, whereas before it was guarded by `args.step in (None, 1, 2, 3, 4)`. The old guard was always true for allowed steps, so this is a harmless simplification, but `split = None` followed by separate step branches is getting hard to follow as steps are added. Style preference only. | No action required; consider a small dict of step functions when Step 6 is added. |
